# Open Agent 工作交接报告

更新时间：2026-09-05  
当前本地检查点：`6c12496 chore: checkpoint production preview`

这份报告用于让新的开发者或协作者在没有完整阅读历史对话的情况下，理解
Open Agent 当前在做什么、已经做到哪里、哪些结论仍然没有证据，以及下一步
需要先决定什么。

## 一、项目在做什么

Open Agent 是一个 Web-first、host-neutral 的自主 Agent 服务。它以 Eve 为
运行时内核，以 assistant-ui 为 Web 交互基础，目标是提供类似 Codex 的
多轮 Agent 工作流，同时可以嵌入 Muses 等 SaaS 宿主。

Eve 负责：

- 模型循环、durable session、Workflow、事件流和断流恢复基础能力；
- Provider 重试、上下文压缩、工具执行和原生子 Agent；
- 每个 durable session 的沙箱和 `/workspace`；
- approval、ask、取消和 session 生命周期。

Open Agent 负责：

- Web 会话列表、消息投影、输入框、工具 UI、恢复和本地化；
- 会话控制器、追加/编辑/取消、FIFO mailbox 和 AgentRun admission；
- 线程存储、租户/主体授权、Host JWT 和宿主适配器；
- 上传资产、扫描、沙箱挂载、静态预览和产物交付；
- Contracts、Client、Host、UI 和 MCP adapter 包。

Muses 是第一个宿主，但不是 Open Agent 的编译期依赖。模型凭据、账单、画布、
宿主工具和第三方连接应通过 Host contract 注入，不能进入 Agent 核心。

## 二、产品定位

产品不应被定义为“把每个用户都变成一台永久在线的远程服务器”。更准确的
定位是两档体验：

1. **轻量聊天模式**：普通用户无需创建沙箱，适合问答、短任务、上传附件和
   获取结果，保持较低成本和较高并发。
2. **云端工作区模式**：用户主动打开 VS Code 工作区后，租用一个会话级活动
   沙箱。Agent、VS Code 和开发服务共享同一个 `/workspace`，用于复杂开发、
   构建、测试、热更新和临时服务预览。

本地 Codex 仍然适合直接操作本机仓库、追求最低延迟、离线工作或需要完全开放
本机网络的开发者。Open Agent Web 的差异化价值是：无需本地配置、跨设备继续
任务、页面关闭后仍可运行、与 Muses 的资产/画布/权限/账单集成，以及受控的
远程计算和团队治理。

“每个会话一个沙箱”是逻辑隔离模型，不意味着每个会话永久占用一台物理机器。
生产形态应当是持久会话和工作区记录 + 按需租用远程沙箱执行实例。

## 三、当前已经完成的能力

### 会话和消息运行时

- Eve durable session、绝对事件游标、有限窗口历史加载和断流恢复；
- 浏览器状态作为缓存，Eve 和服务端记录作为权威来源；
- 追加消息的持久 mailbox、FIFO、幂等提交和安全边界注入；
- 最新用户消息编辑的持久化替换、重复提交抑制和恢复路径；
- 取消、approval、ask、子 Agent 状态和刷新后的恢复投影；
- 只读会话恢复不会更新 `updatedAt`，切换会话只 hydration 当前会话，避免
  因 revision 冲突遍历所有会话的完整事件流。

这些能力已经有 TypeScript、单元测试和相关 E2E 覆盖，但“本地测试通过”不等于
已经有目标宿主上的生产 SLO 证据。历史 UI 中出现过的消息顺序、编辑、追加、
失败提示和刷新恢复问题，后续修改必须优先以 durable server state 和事件游标
为准，不能靠浏览器数组截断或额外的隐式状态修补。

### 沙箱和工具链

- Eve 为每个 durable session 提供独立 `/workspace`，纯聊天不会创建沙箱；
- 首次终端、文件、图像或其他沙箱能力调用时懒加载沙箱；
- 当前沙箱镜像包含 Node/npm、Python、Git、FFmpeg、ImageMagick、ripgrep 和
  Playwright/Chromium；
- Docker、microsandbox、Vercel 后端可选，生产必须显式选择后端和不可变镜像；
- 当前策略默认 `deny-all` 出站网络；
- 当前生产预览基线约为 2 vCPU、2 GiB 内存、512 PID、10 GiB 逻辑工作区配额，
  活动沙箱和等待队列有上限，空闲后释放计算许可；
- Docker 单租户 alpha/staging 可接受，多租户互不信任场景需要 microsandbox、
  Vercel Sandbox 或受审查的远程 microVM。

沙箱资源限制是上限和准入保护，不是单机容量承诺。Docker 停止后的容器仍可能
占用工作区磁盘和 inode，逻辑配额也不能替代宿主机物理磁盘配额。

### 资产和结果交付

- 用户上传使用可恢复的分片 AssetStore，生产路径使用 PostgreSQL 元数据和
  S3/MinIO/R2 对象存储；
- 上传支持所有权校验、分片重试、SHA-256、扫描、租户/主体配额和沙箱挂载；
- `import_asset` 已统一支持资产 ID 和远程 URL，并在需要时导入到当前工作区；
- `publish_preview` 发布有限大小的静态网站并返回带 TTL 的签名 URL；
- `publish_artifact` 发布单个文件或媒体结果，支持别名、版本和带 TTL 的下载/预览；
- 发布字节已经外置到对象存储，PostgreSQL 保留元数据和授权关系。

这些能力分别解决上传安全、跨会话持久化和最终交付问题。即使未来用户通过
VS Code 直接访问工作区，也不应删除对象存储、扫描和不可变结果交付链路；可以
把显式工具调用自动化或从普通 UI 中隐藏。

### 存储、容量和运维

- Agent DB 与 Eve Workflow World 已分离；
- mailbox worker、AgentRun reconciler、资产清理和沙箱清理 worker 已具备；
- 有事件归档、校验和隔离恢复演练，归档 worker 默认关闭，热历史删除尚未授权；
- 有单机容量、流恢复、混合负载、资产上传和沙箱生命周期验证脚本；
- 已验证的保守运行点是：1,000 个 pooled SSE follower、100 个独立 durable
  session、约 12 个并发 AgentRun；16 个并发 AgentRun 的测试出现过一次失败。

这些数字不是“单服务器最多用户数”，也不是 10,000 用户容量证明。它们是在一台
约 4 vCPU、7.3 GiB 内存的测试主机上得到的运行点，Provider 延迟、数据库、
Workflow、沙箱和网关必须分别测量。

## 四、当前明确没有完成的能力

- VS Code 远程工作区桥接；
- 用户和 Agent 共用沙箱的文件监听、终端、端口转发和开发服务 UI；
- 动态 Preview Gateway（进程注册、健康检查、HTTP/WebSocket 代理、重启和
  预览生命周期）；
- 跨进程、跨机器的 Sandbox Scheduler 和全局/租户级活动沙箱租约；
- 受控的开发网络配置、凭据代理和依赖安装策略；
- 多服务项目、长期运行 API、任意 WebSocket、外部回调和正式生产部署；
- 每会话数据库或数据库池的产品契约；
- 10,000 独立在线会话、10,000 活动沙箱和大规模动态预览的实测证据；
- 外部真实宿主上的完整 Provider、数据库、对象存储、扫描器、观测和 SLO 验证。

当前静态发布路径明确不暴露任意沙箱端口，见 [architecture.md](./architecture.md)
和 [deployment.md](./deployment.md)。

## 五、为什么下一步要做“共享会话工作区 + 远程沙箱池”

用户需要的不只是 HTML 文件和几条终端命令，还包括：在浏览器中完成依赖安装、
运行前后端项目、观察热更新、调试服务、查看文件和继续长任务。共享会话工作区
可以让 Agent 和用户看到同一份代码和同一个运行环境，避免“Agent 在一个沙箱、
用户在另一份副本”造成体验和状态分裂。

但如果把所有用户都绑定到常驻沙箱，单机一定会失去并发能力。当前资源上限下，
10,000 个同时活动沙箱的理论上限约为 20,000 vCPU 和 20 TiB 内存，还没有计算
VS Code Server、开发服务、数据库、日志和存储。即使沙箱停止，Docker 工作区、
Workflow 事件和依赖缓存仍可能继续占用磁盘。

因此生产级架构必须把 Agent 控制面和沙箱执行面分开：

```text
Web / VS Code
      │
      ▼
控制面：Auth、Session、Eve、Workflow、Mailbox、配额、事件流
      │
      ▼
全局调度器：租约、租户公平性、队列、资源等级、回收
      │
      ▼
执行面：Docker / microsandbox / 远程 microVM 沙箱池
      │
      ├── 会话工作区 /workspace
      ├── Agent 工具和开发服务
      └── VS Code 与预览网关
      
对象存储：资产、工作区快照、发布产物和归档
```

每个会话仍然只有一个逻辑工作区；计算实例按需租用，空闲后停止，工作区通过
快照、卷或对象存储恢复。这样可以保留本地服务器式体验，同时不会把在线用户数
直接等同于活动服务器数。

## 六、下一步计划

### 阶段 0：先确定产品契约

明确 Open Agent 是“Web-first 云端 Agent 工作区”，还是仅提供轻量聊天和静态
结果。如果选择前者，必须接受远程执行、资源配额和多租户调度是核心基础设施，
不是可选 UI 功能。

同时确定两档模式：轻量聊天默认关闭沙箱；工作区模式由用户主动开启并取得
会话级活动租约。

### 阶段 1：定义会话工作区和租约

- 固定一个会话对应一个逻辑 `/workspace`；
- 定义 active、idle、stopped、expired、restoring 状态；
- 明确文件、终端、进程、端口和 Agent 操作的授权边界；
- 记录资源等级、租户、所有者、使用量和最后活动时间；
- 先限制为每会话一个 IDE 工作区和一个开发服务。

### 阶段 2：接入远程沙箱执行面

- 抽象 Sandbox Adapter，不让 Web 或 Eve 进程直接依赖某个 Docker 容器；
- 引入跨进程/跨机器的全局活动租约、租户配额和有限队列；
- 支持快照、恢复、空闲回收和显式删除；
- 先使用 microsandbox、Vercel Sandbox 或经过验证的远程 microVM；
- Docker 继续作为可信单租户 alpha/staging 后端，不直接承担互不信任的多租户。

### 阶段 3：实现 VS Code 和动态开发预览

- Web 集成优先评估 OpenVSCode Server/code-server；桌面版 VS Code 评估远程文件
  系统扩展；
- 两种客户端都连接同一个会话工作区，不创建副本；
- 提供文件读写、变更监听、终端和会话级端口转发；
- 通过会话授权和临时令牌访问，不暴露容器地址、宿主路径或裸端口；
- 动态预览先支持一个 HTTP 服务，再评估 HMR/WebSocket；
- 支持启动、健康检查、停止、重启、过期和有限日志尾部。

### 阶段 4：网络、依赖和数据库能力

- 默认仍为 `deny-all`；工作区模式提供用户可见的开发网络开关；
- 优先使用域名白名单、出站代理和凭据代理，不把密钥写入沙箱；
- 小任务使用 SQLite；普通项目使用 Host 提供的共享数据库命名空间；
- 独立数据库只作为更高资源等级，由远程服务提供，并设置连接、存储、TTL 和
  费用上限；
- 不为每个用户默认启动 PostgreSQL、Redis 等基础设施。

### 阶段 5：容量和生产发布门槛

- 分别压测连接、独立会话、AgentRun、活动沙箱、VS Code、动态预览、数据库、
  对象存储和事件归档；
- 记录 CPU、RSS、事件循环延迟、队列等待、Workflow/Agent DB 连接池、磁盘、
  inode、网络和重连率；
- 验证超额时有界排队或明确 429，不允许无限等待或重复创建；
- 验证跨租户文件、端口、资产、日志和数据库隔离；
- 验证服务崩溃、Worker 重启、浏览器刷新、沙箱休眠和恢复；
- 只有在目标宿主和目标沙箱后端完成证据后，才决定公开并发和用户规模；
- 正式生产部署、域名、长期运行和回滚继续作为 Host 能力，不阻塞前面的工作区。

## 七、当前最需要继续讨论的困惑点

1. **产品边界**：我们要做的是本地 Codex 的云端补充，还是要承诺完整的 Web
   Codex 工作区？如果是后者，远程沙箱池和调度器必须进入核心路线。
2. **VS Code 形态**：优先嵌入 Web 的 OpenVSCode Server，还是优先支持桌面版
   VS Code 远程扩展？两者的资源和开发成本不同。
3. **工作区持久化**：工作区保留多久，依赖缓存是否保留，停止容器后采用卷、
   快照还是对象存储，用户删除后如何保证物理回收？
4. **网络自由度**：是否允许用户主动开启开发网络？哪些域名可以访问？Git、
   npm、PyPI 和第三方 API 的凭据如何代理？
5. **数据库范围**：第一版是否只支持 SQLite 和 Host 共享数据库，还是需要独立
   临时数据库？后者会显著提高资源和调度复杂度。
6. **服务范围**：第一版是否只支持每会话一个 HTTP 服务，何时加入前后端多服务、
   WebSocket、后台任务和公网回调？
7. **资源等级**：小型、中型、大型任务的 CPU、内存、磁盘、运行时长和价格如何
   定义？一个超出宿主规格的任务应排队、拒绝还是迁移到更大执行池？
8. **结果交付**：工作区模式中 `import_asset` 是否自动化并从 UI 隐藏；静态预览
   和产物发布是否统一成用户可见的“交付”动作；哪些结果需要脱离沙箱长期保存？
9. **容量目标**：10,000 是在线连接目标、持久会话目标，还是同时活动 Agent/沙箱
   目标？这三个指标必须分开，否则会得到错误的单机容量结论。
10. **多租户信任模型**：Muses 是否会让互不信任的租户共享同一执行集群？若是，
    Docker 只能作为受限基线，必须完成 microVM/远程沙箱隔离证据。

## 九、交接原则

- Eve durable state 和服务端数据库是权威来源，浏览器只是投影缓存；
- 所有异步操作必须有稳定 ID、幂等键、所有者和单调状态转换；
- 不为了改善 UI 而删除或重写未知来源的历史事件；
- 不把上下文压缩误认为物理存储回收；
- 不把静态预览、动态开发服务和正式生产部署混成一个接口；
- 不默认给所有在线用户创建活动沙箱；
- 不在没有目标环境实测数据时承诺 1 万或 10 万用户容量；
- 新增复杂度必须对应明确的用户能力或资源/安全约束，并有可验证的回归门槛。
